# コミット作成

変更内容からコミットメッセージを作って、確認後にコミットする。

## 手順

### ステップ1: プロジェクトのコミットスタイルを検出
- `git log --oneline -10` で直近10件のメッセージを確認する
- 日本語か英語か判定する。混在していたら日本語優先
- プレフィックス形式を検出する(feat:/fix: 形式か、括弧付き feat(scope): 形式か、形式なしか)
- 検出できなければデフォルト: `<種別>: <内容>` (日本語)
- 種別の一覧: feat / fix / refactor / test / docs / chore / style / perf

### ステップ2: 変更内容を把握する
- `git diff --staged` でステージ済みの変更を確認する
- `git diff` でステージされていない変更を確認する
- もしステージ済みが空で、未ステージの変更がある場合:
  - ユーザーに「ステージされていない変更があります。`git add` しますか?」と聞く
  - ユーザーが了承したら `git add` する(ただしファイルを明示的に指定。`git add .` は使わない)
- どちらも空なら「コミットする変更がありません」と伝えて終了する

### ステップ3: 秘密情報の検出(コミット前に必ず実行)
- 以下のパターンがステージ済みファイルに含まれていないか確認する:
  - `.env`, `.env.local`, `.env.production` がステージされていないか
  - `credentials.json`, `serviceAccountKey.json` がステージされていないか
  - コード内に `AKIA` (AWS), `sk-` (OpenAI), `ghp_` (GitHub), `xoxb-` (Slack) 等のプレフィックスがないか
  - `password = "..."`, `secret = "..."` のようなハードコードがないか
- 1つでも見つかったら、コミットを中止して「秘密情報が含まれています」と警告する
- .gitignore に `.env*` が入っているかも確認する

### ステップ4: 複数の論理的変更の検出
- 変更ファイルを分析して、複数の無関係な変更が混ざっていないか確認する
- 例: 新機能のコードとバグ修正が同時にステージされている場合
- 混ざっていたら「2つの変更が混ざっています。分けてコミットしますか?」と提案する
  - ユーザーが同意したら、関連ファイルだけ `git add` して1つ目をコミット、残りを次にコミット
  - ユーザーが「まとめていい」と言ったらそのままコミット

### ステップ5: コミットメッセージを作る
- 変更内容から適切な種別を選ぶ:
  - 新しいファイル追加 + 機能追加 → feat
  - 既存コードの修正(バグ) → fix
  - 動作を変えないコード改善 → refactor
  - テストの追加・修正 → test
  - README等の文書 → docs
  - 設定ファイル・依存関係 → chore
- メッセージは50文字以内を目指す
- 「何を」ではなく「なぜ」を書く(例: ×「ボタンの色を変更」→ ○「アクセシビリティ基準を満たすためボタンの色を調整」)
- 本文(body)が必要な場合は空行を挟んで詳細を書く

### ステップ6: ユーザーに確認してコミット
- 作成したメッセージをユーザーに見せる
- ステージされるファイル一覧も表示する
- ユーザーがOKしたら `git commit` を実行する
- コミット後に `git status` で結果を確認する

### テストが失敗した場合
- プロジェクトにテストコマンドがあれば、コミット前に実行を提案する
- テストが失敗したら「テストが失敗しています。修正してからコミットしますか?」と聞く
- ユーザーが「そのままコミット」と言ったら警告付きでコミットする

### pre-commitフックが失敗した場合
- フックのエラーメッセージを読んで原因を特定する
- リントエラーなら自動修正を試みる(`npm run lint:fix` 等)
- 修正後、変更を再ステージして新しいコミットを作る(amendではなく新規)
