# リファクタリング

コードの動作を変えずに、構造を整理してきれいにする。

## 手順

### ステップ1: 対象の読み込み
1. $ARGUMENTS のファイルを読む
2. ファイルのテストが存在するか確認する
3. **テストがない場合**: 「テストがありません。リファクタ前にテストを書くことを強くお勧めします。先にテストを作りますか？」と提案する

### ステップ2: 問題の分析

以下の観点でコードを分析する:

| チェック | 基準 | 例 |
|---------|------|-----|
| DRY違反 | 同じコードが2回以上 | 同じバリデーションロジックが複数箇所 |
| 長すぎる関数 | 30行超 | 1つの関数に複数の責務 |
| 深いネスト | 3段超 | if の中の if の中の if |
| 命名の改善 | 意味が不明確 | `data`, `temp`, `flag` 等 |
| 責務の分離 | 1ファイルに複数の関心事 | UIとビジネスロジックが混在 |
| 不要な複雑さ | 過度な抽象化 | 1回しか使わないのにFactoryパターン |

### ステップ3: 改善案の提示

| 3 | 23 | 命名 | `d` → `userData` | 変数名を明確化 | 小 |

### ステップ4: 修正の適用
1. ユーザーが承認した提案だけ修正する
2. 1つの提案を適用するたびにテストを実行する
3. テストが通らなければ修正を巻き戻す

### ステップ5: 結果の確認
- テストが全て通ることを確認する
- 変更前後の行数・複雑度を比較する

## 失敗時の対処

| 状況 | 対処 |
|------|------|
| テストがない | テスト追加を先に提案。ユーザーが断ったら慎重に進める |
| リファクタが大きすぎる | 「一度に全部は危険です。3段階に分けて進めますか？」と提案 |
| テストが壊れた | 変更を巻き戻して、より小さい単位で再挑戦 |
| 外部から参照されている | 公開APIの変更は影響調査を先に行う |
