# yoshida 要件定義セット

このフォルダは、携帯管理サービスを開発・理解するための要件定義一式である。本リポジトリではシステム実装を行わず、業務・データ・例外をMarkdownで整理する。

## 読む順番

AI開発担当は、次の順に読む。

1. `01-service-overview.md`: サービス全体像、契約、対象機種、窓口、業務範囲
2. `02-org-chart.md`: 組織構造、表記ルール、N/D/K/顧客の関係
3. `03-glossary.md`: 用語定義
4. `04-data-model.md`: 受付管理簿、依頼書3種、月次レポート、お客様情報のスキーマ
5. `05-flow-breakdown.md`: 故障対応
6. `06-flow-lost-device.md`: 盗難紛失時の端末再貸与
7. `07-flow-request-kitting.md`: リクエストキッティング
8. `08-flow-monthly-report.md`: 月次レポート
9. `09-edge-cases.md`: 横断例外、賠償、追加書類、作業停止条件

PM・開発マネージャーが全体像だけを掴む場合は、先に `00-handbook.md` を読む。

## 絶対ルール

| ルール | 内容 |
|---|---|
| 組織名 | `02-org-chart.md` の表記を正とする |
| 用語 | `03-glossary.md` の定義を正とする |
| データ項目 | `04-data-model.md` のスキーマを正とする |
| 原本 | `_source/` 配下は読み取り専用扱い。編集しない |
| PDF | PDFがある原本はPDFを正本として扱う |
| 実データ | 電話番号、IMEI、伝票番号などはマスキングする |

## 組織名の強制

許可表記:
- N（携帯会社）
- N（営業担当）
- N（協力会社管理部門）
- D（レンタルセンター）
- K（ヘルプデスク）
- 企業管理者
- 利用者

禁止:
- レンタルセンターをN名義で書くこと
- 実在会社名、旧社名、支社名を要件定義へ直書きすること
- K（ヘルプデスク）をN内部組織として扱うこと
- D（レンタルセンター）をリクエストキッティングの直接作業担当にすること

## 設計前提

受付システムは代理店ごとに異なる。Excel、kintone、Microsoft Power Appsなどがあり得るため、実装時は `04-data-model.md` の論理項目を中心に、画面・DB・外部連携をプラガブルに設計する。

月次レポートや報告書送付ではPPAPを避ける。企業ごとに許容されたファイル転送サービスを利用する。候補はBox、Dropbox、STORM、eTransporter、クリプト便、Smooth File、GigaFile便などで、案件ごとに確定する。

サンプルに含まれる仮名、伏字、メールアドレス、電話番号、企業名は本番値ではない。実装やテストデータに流用する場合は、必ずマスク済み値または案件別の正式値に差し替える。

## 実装時の優先順位

1. 組織・責務の整合性を保つ。
2. 受付管理簿と依頼書3種のフィールドを取りこぼさない。
3. 各フローのステップ順と差し戻し条件を状態遷移として表現する。
4. 月次レポートは受付システム依存にせず、集計元を差し替え可能にする。
5. 例外は `09-edge-cases.md` の条件を先に確認する。

## 変更時の注意

フロー本文に用語説明を重複して増やさない。共通語は `03-glossary.md`、データ項目は `04-data-model.md`、組織関係は `02-org-chart.md` に集約する。

新しい例外が見つかった場合は、該当フローの例外分岐に短く追加し、詳細は `09-edge-cases.md` に集約する。
