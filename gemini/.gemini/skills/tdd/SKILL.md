# テスト駆動開発 (TDD)

テストを先に書く → 最小限のコードで通す → きれいに整理する。この3ステップを小さく繰り返す。

## 手順

### ステップ1: テストフレームワークの検出
- まずプロジェクトのテスト環境を調べる:
  - `package.json` の `devDependencies` に `vitest` があるか → Vitest
  - `jest` があるか → Jest
  - `pytest` があるか (requirements.txt / pyproject.toml) → pytest
  - `go test` (Goプロジェクト) → Go標準テスト
  - 何も見つからない場合: 「テストフレームワークが入っていません。Vitestを入れますか?」と提案
- テスト実行コマンドを特定する: `npm test`, `npx vitest`, `pytest` 等
- テストファイルの配置ルールを確認する: `*.test.ts`, `*.spec.ts`, `__tests__/` 等

### ステップ2: 対象機能の分解
- ユーザーが作りたい機能をヒアリングする
- 機能を小さなステップに分解する(1ステップ = 1つのテストケース)
- 例: 「ユーザー登録機能」なら:
  1. メールアドレスのバリデーション
  2. パスワードの長さチェック
  3. 重複メールアドレスの拒否
  4. 正常なユーザーの作成
  5. 成功時のレスポンス形式

### ステップ3: RED - 失敗するテストを書く
- 1つのテストケースだけ書く(まとめて書かない)
- テストの名前は「何をテストしているか」が日本語で分かるようにする
- 例 (Vitest):
  ```typescript
  describe('validateEmail', () => {
    it('不正なメールアドレスでfalseを返す', () => {
      expect(validateEmail('invalid')).toBe(false)
    })
  })
  ```
- テストを実行して、失敗することを確認する
- 「コンパイルエラー」と「テスト失敗」は区別する。コンパイルエラーの場合は最低限の型定義だけ作る
- ユーザーに報告: 「RED: テストが失敗しました(期待通り)。次にコードを書きます」

### ステップ4: GREEN - テストを通す最小限のコードを書く
- テストを通すために必要な最小限のコードだけ書く
- 「きれい」にしなくていい。ハードコードでも、冗長でもOK
- 例: 最初は `return false` だけでテストを通すこともある
- テストを実行して、全テスト(今回追加したものだけでなく)が通ることを確認する
- ユーザーに報告: 「GREEN: テストが通りました」

### ステップ5: REFACTOR - コードを整理する
- 重複を消す
- 変数名・関数名を改善する
- 長すぎる関数を分割する
- ただし、動作は変えない
- リファクタリング後にテストを実行して、全テストが通ることを確認する
- リファクタリングすることがなければスキップしてよい
- ユーザーに報告: 「REFACTOR: コードを整理しました。テストは引き続き通っています」

### サイクルの繰り返し
- ステップ2で分解したリストの次の項目に進む
- 1サイクルごとにユーザーに結果を報告してから次に進む
- ユーザーが「もういい」と言ったら途中でもサイクルを終了する

### ユニットテストとインテグレーションテストの使い分け
- ユニットテスト: 1つの関数/クラスを単独でテスト。外部依存はモックする
- インテグレーションテスト: 複数の部品を組み合わせてテスト。DBやAPIも含む
- まずユニットテストでロジックを固める → 最後にインテグレーションテストで結合を確認
- インテグレーションテストはセットアップが重いので、ユニットテストが全部通ってからにする

### テストが先に書きづらい場合
- UI(見た目)のテスト → 先にコードを書いてからスナップショットテストを追加でもOK
- 外部APIとの連携 → モックの設計を先にして、モック相手にテストを書く
- 探索的な実装(何を作るか不明確) → スパイク(試し書き)を先にしてから、テストを後から書く。ただしスパイクのコードは捨てて書き直す
