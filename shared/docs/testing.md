# テスト方針

## ルール
- コードを変えたら検証する
- 「正しい理由で失敗する」最小のテストを優先する
- 動作が変わったらテストを追加・更新する
- テストを通すために黙ってテストを弱めない

## 検証の順番
1. 再現テスト（失敗するテスト）
2. ユニットテスト / 統合テスト
3. 型チェック
4. リント
5. ビルド
6. 全体テスト（必要な時だけ）

## 変更の種類ごとの期待
- バグ修正: 回帰テストを追加
- 新機能: ハッピーパス + 主要エッジケースのテスト
- リファクタ: リスクが高ければ安全確認テストを先に追加
- ドキュメントのみ: コードテスト不要。リンクや例は確認

## 完了条件
タスクは以下が満たされるまで完了ではない:
- 関連するチェックが通る、または
- 未検証の領域が明示的に報告されている
