# 開発ワークフロー

## 基本フロー
1. AGENTS.md と関連 docs/ を読む
2. Brainstorm（/brainstorm）— 何を作る？エッジケースは？
3. Spec（/spec）— 仕様書を作って認識を合わせる
4. Plan（/plan）— タスク分解して plans/ に保存。人間が確認・削る
5. Execute — 小さい差分で実装。差分ごとに検証
6. Review（/review）— 別視点でチェック
7. Ship（/land）— テスト→リント→コミット→push
8. docs/ を更新

## いつ計画が必要か
必要:
- 複数ファイルが変わる
- 設計が変わる可能性がある
- 不慣れな領域
- 要件があいまい

不要:
- 一文で説明できる変更
- タイポ修正
- 設計リスクがない

## セッション管理
- 1タスク = 1セッション。終わったら /clear
- 計画と実装は別セッションで。計画が確定したら plans/ に保存して、新セッションで実装
- コンテキスト使用率 40% 以下を維持
- 40% 超えたらタスクをまとめて新セッションへ
- 70% 超えたら即 /compact するか新セッション

## コミット
- 1つの論理的変更 = 1コミット
- コミット前に scripts/verify.sh を実行
- TDD の場合、テスト作成と実装を別コミットにする

## コードコメント
- 「何を解決するか」を書く。「どうやるか」は書かない
- 複雑なロジック、ビジネスルール、設計判断にだけコメント
- 自明なコードにはコメント不要

## ファイルサイズ
- 500行を超えたファイルは分割を検討する
- 定期的に「500行超のファイルを見つけてモジュール化して」と頼む
- 短いファイル = 速い読み込み = コンテキスト節約 = 高品質な出力

## モデル選択の目安
- Opus: 設計・計画・複雑な判断
- Sonnet: 実装・コードレビュー・修正
- Haiku: 定型作業・検索・ログ分析

## サブエージェント
- 必ず目的文を含める
  - NG:「認証の仕組みを調べて」
  - OK:「レート制限の改善のために、認証の仕組みを調べて」
- 調査・レビュー・ログ分析はサブエージェントに分離する
- メインセッションのコンテキストを守る

## 並列作業（Git Worktree）
複数エージェントで同時に作業する時:
1. git worktree add -b feature-1 ../project-feature-1
2. 各フォルダで別のエージェントを起動
3. 終わったらマージ:
   git checkout main && git merge feature-1
   git worktree remove ../project-feature-1
上限: 1人のレビュアーで統合する場合、3-4エージェントが現実的な上限

## 行き詰まった時
既存コードのパターンに引きずられてループしている場合:
1. 空のフォルダを作る
2. その機能だけを単体で作る
3. 動いたら本体に統合する

## プラン保存 = 元に戻す資産
plans/ に保存したプランは「元に戻す」ためにも使える。
後から「plans/xxx.md を元に戻して」と言えば、git revert より正確に巻き戻せる。
