# AGENTS.md

## ルール
- まず計画を立てる。複数ファイルを変える作業、設計変更、一文で説明できない作業は必ず plan を作ってから実装する
- 最小の正しい差分を出す。動いてるコードを理由なく書き直さない
- 成功を宣言する前に検証する。scripts/verify.sh があればそれを使う
- 既存のパッケージマネージャとタスクランナーに従う。勝手にツールを変えない
- 必要なければ依存パッケージを追加しない
- 生成ファイル、ロックファイル、マイグレーション、シークレット、CI設定はタスクが要求しない限り触らない
- 動作・設計・ワークフロー・テスト方針が変わったら docs/ を更新する
- 迷ったら docs/ を読んでからコードを触る

## コンテキスト管理
- コンテキスト使用率は40%以下を維持する
- 40%を超えたらタスクをまとめて新セッションを開始する
- コンテキストの長さを理由にショートカットしない。要約を早めない。タスクは完全に終わらせる
- 途中で切り上げるくらいなら、新しいセッションを提案する
- 1タスク = 1セッションが基本。タスクが変わったら新しい会話を始める
- 大量のトークンを消費する操作（大きなファイルの全文読み込み、大量のファイル一括生成等）の前に警告する。「これは大量のコンテキストを消費します。続けていいですか？」

## ワークフロー
1. Brainstorm — 何を作る？エッジケースは？忘れてることは？
2. Spec — 理解した内容を docs/spec.md に書き出す。人間が確認
3. Plan — タスクに分解。plans/ に保存。人間が確認・削る
4. Execute — 小さい差分で実装。差分ごとに検証
5. Review — 別視点でチェック（可能なら sub-agent で隔離実行）
6. Ship — /land でテスト→リント→コミット→push→次タスク提案

## 安全境界
- 認証・認可・課金・権限のロジックは慎重に扱う
- DB schema / migration は人間の確認なしに変更しない
- 依存パッケージの追加は人間に確認する
- 本番環境の設定・シークレットは触らない
- CI/CD パイプラインの変更は人間に確認する
- 検証できない変更がある場合は、何が未検証かを明示する

## Anti-bloat
- このファイルは短く保つ
- 毎回必要なルールだけ置く
- 詳細な手順は docs/ か skills/ に逃がす
- 古くなったルールは削除する
- サブディレクトリに AGENTS.md を追加すると、そのフォルダ固有のルールを上書きできる
