# プロジェクト初期化

質問に答えるだけでプロジェクトを丸ごと作る。

## 手順

### ステップ1: 既存状態の確認
- カレントディレクトリに既にファイルがあるか確認する
  - `.git` が存在する場合: 「既にgitリポジトリがあります。新しいプロジェクトとして初期化しますか?それとも既存リポを設定しますか?」と聞く
  - `package.json` や `pyproject.toml` 等がある場合: 「既にプロジェクトファイルがあります。上書きしていいですか?」と確認する
  - 空のディレクトリか新規ディレクトリなら、そのまま進む

### ステップ2: 要件の確認
2つ聞く:
- 「要件定義のファイル（md, txt, pdf 等）はありますか？」
- 「壁打ち（対話で要件を深掘り）しますか？」

この2つは独立。両方ありもOK。

| ファイル | 壁打ち | 流れ |
|---------|--------|------|
| ある | しない | ファイル読み取り → 確認 → ステップ3 |
| ある | する | ファイル読み取り → それをベースに壁打ち → ステップ3 |
| ない | しない | 5つの質問 → ステップ3 |
| ない | する | ゼロから壁打ち → ステップ3 |

**ファイルがある場合**:
1. ファイルを読み込む
2. プロジェクト名、目的、技術スタック、画面・機能、デプロイ先を自動で抽出する
3. 抽出結果をユーザーに見せて「これで合ってますか？」と確認する
4. 壁打ちしない場合 → ステップ3 に進む
5. 壁打ちする場合 → 抽出結果をベースにステップ2a に進む

**ファイルがない + 壁打ちしない場合**: → ステップ2b (5つの質問) に進む
**ファイルがない + 壁打ちする場合**: → ステップ2a (壁打ちモード) に進む

### ステップ2a: 壁打ちモード
要件定義書がある場合はそれをベースに、ない場合はゼロから対話で要件を固める。

1. **そもそも何を解決したい？**
   - 「誰が」「どんな場面で」「何に困ってる」を引き出す
   - 要件定義書がある場合: 「ここに書いてある○○、もう少し詳しく聞いていい？」
   - ない場合: 「まず、誰のどんな悩みを解決したい？」

2. **それをどう解決する？**
   - ユーザーの回答が抽象的なら具体例を出す
   - 「つまり、お客さんがスマホから予約できればいい？」
   - 要件定義書の内容に疑問があれば: 「ここは○○の方がよくないですか？」

3. **誰が使う？**
   - ユーザーの種類を整理する（お客さん / 管理者 / 両方）
   - それぞれ何ができればいい？

4. **最低限これだけあればOKな画面は？**
   - 「まずはこの3画面で十分じゃないですか？」と提案
   - 多すぎたら削る、少なすぎたら足す

5. **技術スタックどうする？**
   - 分からなければ「おまかせでOK。おすすめを選びます」
   - 決まってればそれを採用

6. 壁打ちの結果を **要件定義書 (docs/requirements.md)** として保存（既存ファイルがあれば更新）
7. 「この内容でプロジェクトを作っていい？」と確認してからステップ3に進む

### ステップ2b: ユーザーに5つの質問をする
質問は1つずつ聞く。まとめて聞かない。

1. **プロジェクト名** (英語, kebab-case)
   - 入力がPascalCaseやスペース付きなら、自動でkebab-caseに変換して確認する
   - 例: 「My App」→「my-app」でいいですか?
2. **一言で表す目的**
   - 空欄や曖昧すぎる場合は具体例を出して再度聞く
3. **技術スタック** (フロント / バック / DB)
   - ユーザーが「おまかせ」と言った場合のデフォルト: Next.js + TypeScript / Next.js API Routes / PostgreSQL (Prisma)
   - よくある組み合わせ:
     - Webアプリ: Next.js + TypeScript + Prisma + PostgreSQL
     - API: Express + TypeScript + Prisma + PostgreSQL
     - Python: Flask + SQLAlchemy + PostgreSQL
     - Python(高速): FastAPI + SQLAlchemy + PostgreSQL
   - ユーザーの回答がスタック名だけ(例:「Next.js」)なら、残りの推奨構成を提案する
4. **MVPに含める画面・機能** (3-5個)
   - ユーザーが2個以下しか出さなかったら「もう1-2個追加しませんか?」と提案する
   - 7個以上なら「MVPとしては多いです。優先度の高い5個に絞りませんか?」と提案する
5. **デプロイ先**
   - 分からなければデフォルト: Vercel(フロント) + Railway(バック/DB)
   - 選択肢の例: Vercel, Railway, Fly.io, AWS, Cloudflare Pages

### ステップ3: ファイル生成
回答をもとに以下のファイルの `{{...}}` プレースホルダーを埋める:
- CLAUDE.md (またはAGENTS.md/GEMINI.md等、使用中のエージェントに合わせる)
- docs/architecture.md (技術スタックの図、ディレクトリ構成、API設計の概要)
- docs/tasks.md (各タスクは15分以内で完了できる粒度。最初のタスクは「開発環境のセットアップ」)
- README.md (プロジェクト名、目的、セットアップ手順、技術スタック)
- .env.example (必要な環境変数のテンプレート。値は空にする)

### ステップ4: 技術スタック別の初期設定
- **Next.js**: `npx create-next-app@latest` の設定を確認(App Router推奨、TypeScript有効、Tailwind有効)
- **Express**: package.jsonにscriptsを設定(`dev`, `build`, `start`, `test`, `lint`)
- **Python Flask/FastAPI**: `pyproject.toml` または `requirements.txt` を生成
- 共通: `.gitignore` をスタックに合わせて生成(node_modules, __pycache__, .env.local 等)

### ステップ5: Git初期化
- `git init` を実行(既にあればスキップ)
- .gitignore が正しいか確認(`.env*`, `node_modules/` 等が含まれているか)
- `gh` コマンドが使えるか確認する
  - 使えない場合: 「GitHub CLIがインストールされていません。後で `brew install gh` してリポジトリを作ってください」と案内してスキップ
  - 使える場合: `gh auth status` で認証済みか確認
    - 未認証なら: 「`gh auth login` を先に実行してください」と案内してスキップ
    - 認証済みなら: `gh repo create --private {{PROJECT_NAME}} --source=. --remote=origin` でリポ作成
- 初回コミット: `chore: プロジェクト初期化`
- リモートがあれば `git push -u origin main`

### ステップ6: 進捗ダッシュボードを表示
- docs/tasks.md のタスク一覧を読み込む
- 完了/未完了の数と進捗率を表示する
- 最初にやるべきタスクを案内する
