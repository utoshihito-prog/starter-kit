# コードレビュー

変更されたコードの問題点をチェックして、重要度別にテーブル形式で報告する。

## 手順

### ステップ1: 変更内容の取得
- まず `git diff --staged` でステージ済みの変更を取得する
- 次に `git diff` でステージされていない変更も取得する
- もしどちらも空なら「レビュー対象の変更がありません。先に変更を加えるか `git add` してください」と伝えて終了する
- 変更が500行を超える場合は、ファイルごとに分割してレビューする。一度に全部見ようとしない

### ステップ2: 変更ファイルの一覧を出す
- `git diff --staged --name-only` と `git diff --name-only` でファイル一覧を出す
- 各ファイルの言語・フレームワークを判断する(拡張子やimport文から)
- テストファイルと本体コードを分けて把握する

### ステップ3: 以下の12カテゴリでチェック
1. バグ: ロジックの間違い、off-by-oneエラー、無限ループの可能性
2. 型安全性: any型の使用、null/undefinedチェック漏れ、型アサーション(as)の乱用
3. エラーハンドリング: try-catchの欠落、エラーの握り潰し(空のcatchブロック)、ユーザーへのエラー表示
4. セキュリティ: SQLインジェクション、XSS、ハードコードされた秘密情報、dangerouslySetInnerHTML
5. パフォーマンス: 不要な再レンダリング、N+1クエリ、巨大な配列操作、メモ化の欠落
6. 命名: 変数名・関数名の一貫性、誤解を招く名前、プロジェクト内の命名規則との不一致
7. エッジケース: 空配列、空文字列、0、負の数、境界値の処理
8. 依存関係: 不要なimport、循環参照の可能性、バージョン互換性
9. テスト: テストが変更に対応しているか、新機能にテストがあるか、モックが適切か
10. 可読性: 複雑すぎる条件分岐、マジックナンバー、コメントの過不足
11. 競合状態: 非同期処理の順序、共有状態の同時アクセス
12. API設計: レスポンス形式の一貫性、エラーレスポンスの形式、HTTPステータスコードの適切さ

### ステップ4: 重要度の分類
- CRITICAL: 本番で障害やデータ消失を引き起こす。今すぐ修正が必要
- HIGH: 特定条件でバグになる。リリース前に必ず修正
- MEDIUM: コード品質の問題。近いうちに修正した方がいい
- LOW: スタイルや好みの問題。時間があれば改善

### ステップ5: 結果をテーブル形式で出力

```
## レビュー結果

| ファイル | 行 | 重要度 | カテゴリ | 問題 | 修正案 |
|---------|-----|--------|---------|------|--------|
| src/api/user.ts | 42 | CRITICAL | セキュリティ | SQLインジェクションの可能性 | パラメータ化クエリを使う |
| src/hooks/useData.ts | 15 | HIGH | パフォーマンス | useEffect内で毎回API呼び出し | 依存配列を正しく設定する |
```

### ステップ6: サマリーを追加
- CRITICAL/HIGH/MEDIUM/LOW それぞれの件数を数える
- 全体的な品質の判定を1行で書く(例: 「セキュリティに1件重大な問題あり。修正後にマージ可能」)
- CRITICALが1件でもあれば「マージ不可」と明記する

### 大きな差分への対応
- 差分が500行を超える場合: ファイルごとに分割してレビューし、最後にまとめる
- 差分が1000行を超える場合: 「変更が大きすぎます。PRを分割することを強くお勧めします」と最初に伝える
- バイナリファイルや自動生成ファイル(lock系, .min.js等)はスキップする
