# 仕様書作成

コードを書く前に「何を作るか」を文書化して、認識のズレを潰す。
**仕様書にないものは作らない。仕様書にあるものは必ず作る。**

## パイプライン上の位置

```
【/spec ← いまここ】→ /plan → docs/tasks.md → 実装開始
```

- 入力: docs/product.md、$ARGUMENTS のいずれか
- 出力: `docs/spec.md`（または `docs/spec-[機能名].md`）

## 手順

### ステップ1: 入力の収集

以下の優先順位で情報を集める:

1. `docs/product.md` が存在するか確認する
   - あれば読み込んで、プロダクト要件を把握する
2. $ARGUMENTS が指定されている場合はそのテーマで作成する
3. 何もなければユーザーに「何の仕様書を作りますか？」と聞く

### ステップ2: 既存システムとの整合性チェック

1. `docs/architecture.md` を読んで技術スタックと設計方針を把握する
2. 既存コードを走査して:
   - 同名または類似の機能が既にないか確認する
   - 再利用できるコンポーネント/APIを特定する
   - DBスキーマ変更が必要か判断する
3. 矛盾がある場合:
   - 「既存の設計では○○ですが、この機能は○○を前提としています。どちらに合わせますか？」と確認する

### ステップ3: 仕様書の作成

以下のフォーマットで作成する。**各セクションは省略しない。**

```markdown
# 仕様書: [機能名]

## 何を作るか（一言）
[1文で。「○○が○○できる機能」の形式]

## ユーザーストーリー
- [ ] [誰]が[何をした時]、[何が起きる]
- [ ] [誰]が[何をした時]、[何が起きる]
- [ ] ...
（チェックボックス付き。実装時にここを受入テストの基準にする）

## 画面仕様（UIがある場合）

### [画面名1]
```
┌─────────────────────────┐
│  ヘッダー                │
├─────────────────────────┤
│                         │
│  [ASCII ワイヤーフレーム]  │
│                         │
├─────────────────────────┤
│  フッター                │
└─────────────────────────┘
```

- 入力項目:
  | 項目名 | 型 | 必須 | バリデーション |
  |--------|-----|------|-------------|
  | メール | email | ○ | 形式チェック |
  | パスワード | password | ○ | 8文字以上 |

- 操作フロー:
  1. ユーザーがフォームに入力する
  2. 「送信」ボタンを押す
  3. バリデーション → 成功なら次の画面に遷移

## API仕様（APIがある場合）

### [エンドポイント名]
| 項目 | 内容 |
|------|------|
| メソッド | POST |
| パス | /api/users |
| 認証 | 不要 |

リクエスト:
```json
{
  "email": "user@example.com",
  "password": "securepass123"
}
```

レスポンス（成功 201）:
```json
{
  "id": "uuid",
  "email": "user@example.com",
  "createdAt": "2026-03-29T00:00:00Z"
}
```

レスポンス（エラー 400）:
```json
{
  "error": "validation_error",
  "message": "メールアドレスの形式が正しくありません"
}
```

## データモデル（DB変更がある場合）

```
┌──────────┐     ┌──────────┐
│  users   │────<│  posts   │
├──────────┤     ├──────────┤
│ id (PK)  │     │ id (PK)  │
│ email    │     │ user_id  │
│ name     │     │ title    │
└──────────┘     └──────────┘
```

| テーブル | カラム | 型 | 制約 |
|---------|--------|-----|------|
| users | id | UUID | PK |
| users | email | VARCHAR(255) | UNIQUE, NOT NULL |

## 技術的な制約
- 使用技術: [既存スタックに従う]
- 外部API: [使う場合はAPIドキュメントのURL]
- パフォーマンス: [目標。例: レスポンス200ms以内]

## エッジケース
| # | ケース | 期待される動作 |
|---|--------|-------------|
| 1 | メールが既に登録済み | 「このメールは使用済みです」エラー |
| 2 | パスワードが短すぎる | バリデーションエラー表示 |
| 3 | サーバーダウン | 「しばらくしてから再試行」メッセージ |

## やらないこと（スコープ外）
- [明確にスコープ外であることを列挙]
- [「あとで」やることも区別して書く]

## 受け入れ条件
- [ ] [条件1: 具体的で検証可能]
- [ ] [条件2: 具体的で検証可能]
- [ ] [条件3: 具体的で検証可能]
（全部チェックが付いたら完成）

## 非機能要件
- パフォーマンス: [レスポンス時間、スループット]
- セキュリティ: [認証要否、入力サニタイズ]
- アクセシビリティ: [キーボード操作、スクリーンリーダー]
```

### ステップ4: アラートの確認

仕様の内容から以下を自動検出して警告する:

- **認証・認可の変更** → 「セキュリティに影響する変更です。/security-check を実装後に実行してください」
- **外部API依存** → 「外部APIの障害時のフォールバックを検討してください」

### ステップ5: 保存と確認

1. `docs/spec.md` に保存する（複数の仕様がある場合は `docs/spec-[機能名].md`）
2. ユーザーに全文を見せて確認する:
   「この仕様で合ってますか？修正があれば教えてください」
3. 修正があれば反映してもう一度確認する

### ステップ6: 次のステップへの案内

```
仕様書を docs/spec.md に保存しました。

次のステップ:
  /plan → この仕様をタスクに分解する
```

## エッジケース

### 既存の仕様書がある場合
- `docs/spec.md` が既にある場合: 「既存の仕様書があります。上書きしますか？別名で保存しますか？」と聞く
- 別名の場合: `docs/spec-[機能名].md` で保存する

### 仕様が大きすぎる場合
- ユーザーストーリーが10個を超えたら「スコープが大きいです。Phase分けしますか？」と提案する

### 技術スタックが未定の場合
- docs/architecture.md がない場合: 技術制約セクションは「TBD（/auto または初回設定で決定）」にする
