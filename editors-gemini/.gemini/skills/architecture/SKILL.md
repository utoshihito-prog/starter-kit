# 設計チェック

コードベースの設計をSOLID原則・クリーンアーキテクチャの観点でチェックする。

## 手順

### ステップ1: プロジェクト構造の把握
1. ディレクトリ構成を走査する
2. エントリポイントを特定する
3. モジュール間の依存関係を追う（import/require文を分析）

### ステップ2: 以下の6カテゴリでチェック

| カテゴリ | チェック内容 |
|---------|------------|
| 単一責任 | 1つのクラス/モジュールが複数の仕事をしていないか |
| 開放閉鎖 | 拡張しやすく、修正が少なくて済む設計か |
| 依存性逆転 | 上位モジュールが下位モジュールに直接依存していないか |
| 循環依存 | モジュール間で循環参照がないか |
| レイヤー分離 | UI/ロジック/データアクセスが分離されているか |
| God Object | 責務が肥大化したクラス/ファイルがないか（300行超を目安） |

### ステップ3: 依存関係の図を作る

```
┌──────────┐     ┌──────────┐
│  Pages   │────>│  Hooks   │
└──────────┘     └────┬─────┘
                      │
                      ▼
┌──────────┐     ┌──────────┐
│  Utils   │<────│  API     │
└──────────┘     └────┬─────┘
                      │
                      ▼
                 ┌──────────┐
                 │    DB    │
                 └──────────┘
```

### ステップ4: 結果を出力

```
## 設計チェック結果

### 依存関係図
[上記のASCII図]

### 問題点

| # | 場所 | 原則 | 重要度 | 問題 | 改善案 |
|---|------|------|--------|------|--------|
| 1 | src/api/users.ts | 単一責任 | HIGH | バリデーション+DB操作+レスポンス整形が1関数 | レイヤーに分割 |
| 2 | src/utils/index.ts | God Object | MEDIUM | 500行のユーティリティファイル | 機能別に分割 |
| 3 | src/hooks → src/api | 循環依存 | HIGH | hooks が api を、api が hooks を参照 | 共通インターフェースを抽出 |

### サマリー
- 重要度HIGH: X件
- 重要度MEDIUM: X件
- 全体評価: [1文で]
```

## エッジケース

| 状況 | 対処 |
|------|------|
| プロジェクトが小さすぎる | 「ファイル数が少なく、設計チェックの効果は限定的です」と伝える |
| フレームワークの制約 | フレームワーク固有の構造（Next.js App Router等）は問題として報告しない |
| テスト・設定ファイル | テストコードや設定ファイルはチェック対象外にする |
