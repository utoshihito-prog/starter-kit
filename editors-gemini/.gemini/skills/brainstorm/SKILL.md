# ブレインストーミング

コードを書く前に「本当にそれでいい？」を深掘りする対話。
**最低3つの案を出して比較する。1案だけで突っ走らない。**

## パイプライン上の位置

```
【/brainstorm ← いまここ】→ /spec → /plan → docs/tasks.md → 実装開始
```

- 入力: $ARGUMENTS（テーマ）
- 出力: `docs/brainstorm-[テーマ].md`

## 手順

### ステップ1: 問題の定義

$ARGUMENTS のテーマを受け取り、以下を明確にする:

1. **誰が困ってる？**（ユーザーの種類）
2. **どんな場面で？**（具体的なシナリオ）
3. **何に困ってる？**（現状の痛み）
4. **それが解決されると何が嬉しい？**（ゴール）

ユーザーの回答が抽象的なら具体例を出して掘り下げる:
- NG: 「使いにくい」→ OK: 「一覧画面から目的のデータを探すのに5回以上スクロールが必要」
- NG: 「遅い」→ OK: 「ページ読み込みに3秒以上かかっていて離脱率が高い」

### ステップ2: 既存システムの確認

コードベースがある場合:
1. 似た機能や関連する実装があるか確認する
2. 使える既存のコンポーネント/ライブラリを把握する
3. 技術的な制約（使用中のフレームワーク、DB等）を確認する

ない場合（新規プロジェクト）:
- 「技術スタックに希望はありますか？」と聞く

### ステップ3: 案の発散（最低3つ）

以下の切り口で**最低3つ**の解決策を出す:

| 切り口 | 説明 |
|--------|------|
| 最小工数案 | いま一番早く作れる方法。妥協はあってもいい |
| 王道案 | 業界のベストプラクティスに沿った方法 |
| 攻めた案 | 新しい技術やアプローチ。リスクはあるが将来性がある |

各案に以下を記述する:
- **概要**: 何をどう作るか（1〜2文）
- **メリット**: なぜこの案がいいか（具体的に）
- **デメリット**: 何が犠牲になるか（具体的に）
- **工数**: S（1日以内）/ M（数日）/ L（1週間以上）
- **リスク**: 何が起きたらまずいか

### ステップ4: 比較マトリックス

案を横並びで比較する:

```
| 観点 | 案1: 最小工数 | 案2: 王道 | 案3: 攻め |
|------|-------------|----------|----------|
| 工数 | S | M | L |
| 拡張性 | 低 | 高 | 高 |
| ユーザー体験 | △ | ○ | ◎ |
| 技術リスク | 低 | 低 | 中 |
| 保守性 | △ | ○ | ○ |
```

### ステップ5: 決定

1. ユーザーに比較表を見せる
2. 「どの案がいいですか？」と聞く
3. 決まったら**決定理由**も記録する（後で「なぜこうしたか」を振り返れるように）

ユーザーが迷っている場合:
- 「まずは案1で素早く動くものを作って、後から案2に移行する手もあります」等の段階的アプローチを提案する

### ステップ6: ファイルに保存

`docs/brainstorm-[テーマ].md` に以下のフォーマットで保存する:

```markdown
# ブレスト: [テーマ]

## 解決したい問題
- 誰が: [ユーザー]
- 場面: [シナリオ]
- 困ってる: [痛み]
- ゴール: [理想状態]

## 案1: [名前]
- 概要: ...
- メリット: ...
- デメリット: ...
- 工数: S/M/L
- リスク: ...

## 案2: [名前]
...

## 案3: [名前]
...

## 比較表
| 観点 | 案1 | 案2 | 案3 |
|------|-----|-----|-----|
...

## 決定: 案X — [名前]
## 決定理由
[なぜこの案にしたか]
```

### ステップ7: 次のステップへの案内

保存後、以下を案内する:

```
ブレスト結果を docs/brainstorm-[テーマ].md に保存しました。

次のステップ:
  /spec  → この案を元に仕様書を作る（認識のズレを潰す）
  /plan  → すぐにタスク分解に進む（仕様が明確な場合）
```

## エッジケース

### テーマが広すぎる場合
- 「範囲が広すぎます。まずは○○の部分に絞りませんか？」とスコープを狭める

### ユーザーが既に案を決めている場合
- 無理に3案出さない。「他の案も検討しますか？それとも○○案で進めますか？」と聞く
- 進める場合はステップ5（決定）に直接進む

### 既存システムとの統合が必要な場合
- 既存コードの制約を明示して、案に反映する
- 「既存の○○を活かすなら案2が自然です」等、具体的に推薦する
